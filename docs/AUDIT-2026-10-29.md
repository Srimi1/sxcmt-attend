# Bug audit — 29 October 2026

Audited from `8bc617cd51e76d95ab82aeb03569a695312afbc7`. This is a targeted code review and regression pass, not a guarantee that the app has no other bugs. No backend migrations, production data, deployments, or releases were changed.

## Fixed

- **Attendance history:** timetable edits now freeze previously assumed attendance, preserve legacy mark snapshots, and record an effective-time cutoff. New session IDs cannot backfill elapsed dates or count a slot already occupied by a saved historical period. The cutoff survives mode switches, repeated edits, and clock rollback.
- **Teaching end:** tracking respects term end even without a sheet baseline; a baseline's own term end survives save/reopen.
- **Time-sensitive counts:** visible attendance screens refresh at minute boundaries and when returning to the foreground, without requiring another user action. AM/PM end times no longer count afternoon periods in the morning.
- **Forecast:** hidden subjects stay excluded from both the selected scenario and the attend-all comparison, while explicit historical marks still count.
- **Sheet entry:** collapsing subject inputs no longer deletes counts. Counts for subjects removed from the timetable remain editable, and incomplete/invalid subject rows cannot silently disappear on save.
- **Period marking:** bulk P/A actions omit cancelled periods instead of leaving latent marks that reappear when cancellation is undone.
- **Timetable editing:** existing custom subject titles survive time/period edits.
- **Routine state:** future-only versions no longer activate early; same-date upcoming revisions choose the newest. Switching classes resets class-specific version counters. Malformed cached history entries are skipped individually instead of making all attendance unreadable.
- **Stale sync:** class/account context changes invalidate delayed routine responses, including checking the generation inside the serialized repository write. A late response cannot restore cleared class data.
- **Recovery wording:** 100% targets with past absences are described as unreachable through future classes alone, not as requiring “null classes.”

## Known remaining issues and limits

1. **Historical “No class” undo:** cancelling a saved period whose ID no longer exists in the current timetable deletes its only snapshot; the row can disappear and undo cannot reconstruct that historical attendance. The existing specification explicitly requires dropping the mark. That contract was preserved rather than silently changing undo to restore the old mark. A separate historical-period model or an explicit product decision is needed.
2. **Late credential persistence:** `RoutineClient.refresh()` and OTP completion can store credentials after `forget()` clears them. The ViewModel generation fence fixes stale class-state adoption, not this client-level token race.
3. **Rotated join codes:** routine refresh currently reloads history and owner status, not the current join code, so another member/device can retain an obsolete code.
4. **Bounded history:** the backend returns the newest ten versions. Many future-dated versions can evict the version currently in force. The client now refuses to apply a future version early, but needs the active version fetched/preserved separately for correct first-time adoption.
5. **Backend verification gate:** repository instructions require the InsForge `fetch-docs`/`fetch-sdk-docs` MCP tools before integration edits; neither is available in this environment. The HTTP client, SQL migrations, and live backend were left unchanged. Authenticated signup/session/routine/quota/RLS checks remain unverified. Client comments about server-side logout revocation also need verification against the deployed provider implementation.

No merge or deployment is implied by passing the local checks.
